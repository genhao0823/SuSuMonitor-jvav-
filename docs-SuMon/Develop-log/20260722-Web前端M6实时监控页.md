## 关键设计要点

- **一次性 ticket + URL Query**:不把 JWT 放 URL,先调 `POST /api/ws/monitor-ticket`
  拿一次性 ticket,再连接 `ws://.../ws/monitor?ticket=xxx`。后端按 ticket 反查连接身份。
- **`MonitorWebSocket` 重连策略**:3 秒固定间隔重连,不指数退避(SPA 短会话场景下
  频繁可访问比背压更重要)。
- **`history-card` 顶栏** 显示采样条数,空数据时 `el-empty` 兜底。
- **`PageHeader` `actions` slot** 接管"实时连接"标签,布局与 ServerList/AdminUsers 一致。
- **`applyRealtime`** 不追加 history,只覆盖 `latest`,避免历史表被单条实时消息污染。
  `history` 仅由 `load()` 一次性 24h REST 拉取。

## 修复 — M4 遗留 page_size 越界(2026-07-22)

**背景**:M6 实测阶段,创建 server 后列表仍显示"暂无服务器",前端报 40002
`INVALID_REQUEST_PARAMETER`。排查发现前端硬编码的 `page_size` 超出后端 OpenAPI
约束,阻塞 M6 验收。

**症状**(用户报告的栈):
```
GET http://127.0.0.1:5173/api/servers?page=1&page_size=999&sort_by=id&sort_order=desc
→ 400 (Bad Request) → invalid request parameter
fetchList @ ServerListView.vue:367
reload @ ServerListView.vue:379
(由 ServerFormDialog.vue:393 handleSubmit 触发,即创建成功后 reload 失败)
```

**附带诊断**:`ServerFormDialog.handleSubmit` emit success 后才触发 reload,
说明 **POST /api/servers 创建实际成功了**;数据库里已经有 1 条 server。
reload 的 400 让列表显示空,用户误以为没创建。

**根因**:
| 项 | 值 |
|---|---|
| 前端 | `ServerListView.vue:301` `page_size: 999`(硬编码"拉全") |
| 后端约束 | `openapi-server.json:543` `"page_size": {"type": "integer", "minimum": 1, "maximum": 100}` |
| 校验失败 | 40002 INVALID_REQUEST_PARAMETER |

**修复**(1 行 + 1 注释):
```diff
- page_size: 999,
+ page_size: 100,
```

注释同步:`ServerListView.vue:298-300` 说明 OpenAPI max=100 来源,后续 catch-up
避免再次硬编码魔法数字。

**Commit**: 本次 fix commit 单独立 commit,见 git log。

**教训**:
1. **前端硬编码魔法数字**前必须核对 OpenAPI schema 的 max/min 约束。
2. **`npm run openapi:check` 仅校验 OpenAPI JSON 结构**,**不校验请求体字段值约束**,
   这是结构性 lint 的局限,需要 e2e 测试兜底。
3. **catch-up commits** (B1-B5) 从未经过端到端浏览器实测,本次 M4 page_size bug
   暴露了这个流程漏洞——下次重大 catch-up 后**必须 e2e 至少跑一次所有"用户可见路径"**。
4. **零删除 + 修复可追溯**:用户实测报错 → 我退出 Plan Mode 给修复计划 → 用户确认
   → 我执行 1 行修复 + 1 行注释 + dev-log 段同步 + 1 commit。**全部留痕**。

**回归保障**:本批 catch-up + M6 + M4 fix 完成后,再跑一次 typecheck/lint/openapi:check
全绿,B 阶段的"未实测代码"风险得到兜底。
