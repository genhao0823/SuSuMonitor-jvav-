## 二、基线目的

为后续 MVP-10 Metrics Outbox 和 MVP-11 Alert 消费者拆分提供可比较的模块化单体基线。当前链路仍为本地 Spring 事务事件：

```text
Metrics 入库 -> MetricsReportedEvent -> Alert 评估/写库 -> AlertTriggeredEvent -> alert.push
```

该基线不代表 RabbitMQ 延迟、吞吐或可靠性结果。

## 四、固定场景

1. 单服务器、少量规则：确认单次指标上报和单规则评估基线。
2. 单服务器、多规则：确认规则匹配与告警写入随规则数变化的延迟。
3. 多服务器并发上报：记录 Metrics 事务和本地事件调度在并发下的 p50/p95/p99。
4. 持续越界：确认持续状态不重复生成记录时的评估耗时和异常率。
5. 恢复后再次越界：确认恢复删除状态、再次触发和推送的链路耗时。
6. 重复 `message_id`：记录幂等命中比例和不产生额外告警的结果。
7. Monitor 订阅者数量变化：记录从告警事务提交到 WebSocket 推送完成的延迟。

## 五、指标口径

- Metrics 上报：请求/WS 入口到数据库事务完成的耗时，报告吞吐、p50、p95、p99、错误率、重复比例和乱序拒绝比例。
- Alert 评估：事件进入评估器到告警评估事务完成的耗时，按单规则和多规则报告 p50/p95/p99。
- 本地事件：Metrics 事务提交到 Alert 评估开始，以及 Alert 事务提交到 WebSocket 推送完成的耗时。
- 数据库：指标写入、规则查询、告警记录写入和状态写入耗时；记录锁冲突/事务失败次数。
- 正确性：首次越界一条记录、持续越界不重复、恢复为 `resolved`、再次越界生成新记录；重复消息不产生额外副作用。

除 p50/p95/p99 外不得只报告平均值。每个场景需同时记录样本数、并发、持续时间、异常数和数据清理结果。

## 六、执行和安全边界

- 只使用已备份且名称包含 `validation` 的隔离数据库，禁止在开发库或生产库进行压测写入。
- 执行前确认数据库备份存在、非空且可读取；测试结束核对临时数据清理和 Flyway 状态。
- 当前项目已有 MVP-6 HTTP/WebSocket 验收脚本 `api-test/verify-alert-ws.mjs`，可作为业务正确性回归资产；它不是性能压测工具，不能直接将其单次结果当作吞吐基线。
- 如需新增压测脚本，应先固定输入规模、并发、持续时间、输出格式和清理策略，再补充到本日志。
