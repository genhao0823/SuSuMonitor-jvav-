## 难题 1：WebSocket 反向终端中继 + 三段链路 + 双层字节限流 + Monitor 背压

> **难度**：⭐⭐⭐⭐⭐（多组件联动 + 一端故障整条崩 + 边界情况极多）

### 1. 问题现象

MVP-7 目标：用户在浏览器里打开 `/terminal/{serverId}`，像 SSH 客户端一样登入 Linux bash，PTY 由 Go Agent 端本地拉起。

实现路径上遇到一组问题：

1. **链路复杂**：浏览器到 bash 之间要跨 3 段（Vue→Java 中继→Go Agent），任何一段断，整条挂。
2. **慢消费者雪崩**：浏览器切到后台 tab 时，Java `sendMessage` 在 IO 队列里无限堆积，最后把 JVM 内存打爆。
3. **带宽失控**：用户按住 `↑` 不放，Go Agent 把数据灌到 OutputStream，Java 来不及转发，缓冲爆炸。
4. **协议字段走私**：浏览器发一帧 `terminal.input` 数据量不设上限，攻击者可以发 10 MB 一帧把整个会话卡死。
5. **会话资源耗尽**：同一个用户开 100 个终端，DDOS 自己的服务。

### 2. 根因分析

关键代码片段（**改造前**）：

```java
// 改造前：直接 sendMessage，无任何背压 / 限流
@Override
public void sendInput(WebSocketSession monitor, TerminalInputPayload p) {
    AgentWebSocketSession agent = relay.find(p.sessionId);
    agent.sendMessage(new TextMessage(json(p)));  // 慢消费者阻塞
}
```

```go
// 改造前：Go Agent 无输出限流
func (s *Session) pump() {
    buf := make([]byte, 4096)
    for {
        n, _ := s.Ptmx.Read(buf)
        ws.WriteMessage(websocket.BinaryMessage, buf[:n])  // 全速灌
    }
}
```

根因：**每个组件都假设对端是健康的**。WS 是无内建流量控制协议（不像 HTTP/3 的流控制），所有背压都得应用层实现。

### 3. 解决思路

四个独立防御层叠加：

| 层 | 防御对象 | 机制 | 阈值 |
|---|---|---|---|
| 控制帧限流 | 浏览器恶意或失控 | JVM 内存 Token Bucket，按 (Monitor, sessionId) 分桶 | open 6/min、input 600/min、resize 60/min、close 30/min |
| 输出字节限流 | 单会话带宽 | Token Bucket（Go + Java 双层） | 256 KiB/s + 512 KiB burst |
| Monitor 背压 | 慢浏览器 | `ConcurrentWebSocketSessionDecorator(TERMINATE)` | 5s send time limit + 256 KiB buffer |
| 配额锁 | 全局资源滥用 | `ReentrantLock` 单 JVM | 用户 2 / 服务器 4 / 全局 16 |
| 协议层白名单 | 字段走私 | `TerminalProtocolValidator` 显式白名单 + 16 KiB 上限 | — |
| 双重关闭收口 | 中途断连 | `TerminalRelayLifecycleService` 双端同时关 | — |

#### 4.1 Java 双层限流

```java
// websocket/TerminalMessageRateLimiter.java (简化)
private final ConcurrentMap<String, TokenBucket> buckets = new ConcurrentHashMap<>();

public boolean tryAcquireControlFrame(String monitorSessionId, String serverSessionId, FrameType type) {
    var spec = switch (type) {
        case OPEN   -> new Spec(6,  2);    // open 6/min, burst 2
        case INPUT  -> new Spec(600, 120);  // input 600/min, burst 120
        case RESIZE -> new Spec(60, 20);    // resize 60/min, burst 20
        case CLOSE  -> new Spec(30, 10);    // close 30/min, burst 10
    };
    return buckets.computeIfAbsent(monitorSessionId + ":" + serverSessionId, k -> new TokenBucket(spec)).tryConsume(1);
}
```

```java
// websocket/TerminalOutputRateLimiter.java (简化)
public boolean tryAcquireOutputBytes(String sessionId, int bytes) {
```

#### 4.2 Go 端同步实现

```go
// internal/terminal/output_limiter.go
type TokenBucket struct {
    mu         sync.Mutex
    tokens     float64
    capacity   float64
    refillRate float64
    lastRefill time.Time
}

func (b *TokenBucket) Wait(ctx context.Context, n int) error {
    for {
        b.mu.Lock()
        b.refill(time.Now())
        if b.tokens >= float64(n) {
            b.tokens -= float64(n)
            b.mu.Unlock()
            return nil
        }
        b.mu.Unlock()
        select {
        case <-time.After(b.untilNext(float64(n))):
        case <-ctx.Done():
            return ctx.Err()
        }
    }
}
```

### 6. 收获

1. **WS 无内建流量控制**：所有背压都得应用层实现；`ConcurrentWebSocketSessionDecorator` 是 Spring 6.2.8 的官方解决方案。
2. **多组件联动要分层防御**：协议层白名单 → 输入限流 → 输出限流 → 背压 → 配额 → 关闭收口；任何一层漏了都会被攻击。
3. **两侧对称**：Go Agent 端不能假设 Java 是健康的；Java 端不能假设 Go 是健康的；所以**双层 Token Bucket** 是必要的。
4. **协议字段白名单远比"防黑名单"安全**：不能用 `JsonNode.has(key)` 检查，要在解析后用严格类型 + 范围 + 长度验证。
5. **可深入追问**：WS 限流为什么用 JVM 内存而不是 Redis？（单 JVM 限流性能 1000x；如果引入 Redis，单会话延迟 + 5-20ms，但这是在多实例阶段才值得做。）

## 难题 2：告警状态机 + 乐观锁 + 唯一索引"业务一致性三件套"

> **难度**：⭐⭐⭐⭐（业务领域设计典范）

### 1. 问题现象

MVP-6 目标：让管理员配规则（如 CPU > 80% 报警），Agent 上报指标后触发告警。

实现过程中遇到三个问题：

1. **持续越界产生 N 条 record**：CPU 一直 > 80%，每 5 秒一次上报，每次都写一条 alert_record，最后一秒有 12 条一样的记录。
2. **完全相同的规则可重复入库**：(CPU, >, 80, warning, server=null) 创建 10 次全部成功，前端 toast 显示"创建成功"。
3. **恢复状态机缺位**：CPU 恢复了，但 state 没更新成 `active=false`，下次再越界又写新 record。

### 2. 根因分析

```java
// 错误实现 1：if-else 简单版
if (current > threshold && !alreadyTriggered) {
    recordMapper.insert(new AlertRecord(...));  // 持续越界会持续 insert
    alertState.setActive(true);
}
// 没 "ContinueBreached" 和 "Resolve" 概念

// 错误实现 2：唯一索引直接放 (server_id, metric, operator, threshold_value, level)
// → server_id 允许 NULL，MySQL 多个 NULL 不冲突 → 5 元组无法唯一约束

// 错误实现 3：状态机没版本号
UPDATE alert_states SET active=true WHERE rule_id=? AND server_id=?
// 并发评估会写花
```

根因：**业务一致性需要"状态字段 + 状态机 + DB 唯一约束"三层防御**，单一层都不够。

### 3. 解决思路

**三件套**：

| 件 | 角色 | 实现 |
|---|---|---|
| 状态表 `alert_states` | 当前越界状态 + 乐观锁版本号 | V10 Flyway + `version INT` 字段 |
| 状态机 sealed interface | 4 transition 显式定义 | Java 21 sealed interface |
| 唯一索引 `uk_alert_rules_active_signature` | DB 层防 5 元组重复 | V13 生成列 + UNIQUE 索引 |

```java
// module/alert/service/AlertStateMachine.java
public sealed interface Transition permits Trigger, ContinueBreached, Resolve, NoAction {}

public record Trigger() implements Transition {}
public record ContinueBreached() implements Transition {}
public record Resolve() implements Transition {}
public record NoAction() implements Transition {}

public Transition evaluate(AlertStateEntity s, MetricSnapshot cur) {
    boolean breached = cur.breached();
    if (s == null && breached) return new Trigger();
    if (s == null) return new NoAction();
    if (s.active && breached) return new ContinueBreached();
    if (s.active && !breached) return new Resolve();
    return new NoAction();
}
```

```sql
DELETE r1 FROM alert_rules r1
INNER JOIN alert_rules r2
```

#### 4.3 评估 + 乐观锁

```java
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
@Transactional(propagation = Propagation.REQUIRES_NEW)  // 显式，不能用默认
public void onMetricsReported(MetricsReportedEvent ev) {
    var rules = ruleMapper.selectEnabledForServer(ev.serverId());
    for (var rule : rules) {
        var transition = stateMachine.evaluate(
            stateMapper.find(rule.id(), ev.serverId()),
            snapshot(rule, ev)
        );
        switch (transition) {
            case Trigger t -> {
                Long recId = recordMapper.insert(...);
                stateMapper.insert(new AlertState(rule.id(), ev.serverId(), true, recId, 0));
                publisher.publishEvent(new AlertTriggeredEvent(recId));
            }
            case ContinueBreached cb -> {
                int rows = stateMapper.touch(s.id(), s.version());  // UPDATE ... SET version=version+1 WHERE id=? AND version=?
                if (rows == 0) log.warn("version conflict, recompute");  // 并发被乐观锁拒，下次重评
            }
            case Resolve r -> {
                recordMapper.markResolved(s.alertRecordId());
                stateMapper.markInactive(s.id(), s.version());
            }
            default -> {}
        }
    }
}
```

> **坑**：Spring 6.2 拒绝 `@TransactionalEventListener(AFTER_COMMIT)` + 默认 `@Transactional` 组合；必须显式 `REQUIRES_NEW`。源代码见 `20260725-V11真实验证与P2-1限流实现.md`。

### 5. 真实验证

- Apifox 30 断言真实业务链路：`20260728-MVP6告警运行时验收资产.md`；
- 完整状态机路径 `Trigger → ContinueBreached → Resolve` 三态在真实 MySQL 通过；
- V13 迁移在生产数据先 dedup 再加索引，全程幂等；
- 单元测试 50+ 用例覆盖 4 transition + 并发评估冲突。

### 6. 收获

1. **业务一致性需要"三道防线"**：应用层校验 + 状态机 + DB 唯一索引，单一层次都不够。
2. **MySQL UNIQUE 索引对 NULL 的特殊性**：多个 NULL 不冲突，所以要"生成列把 NULL 转具体值"。
3. **Spring 6.2 @TransactionalEventListener(AFTER_COMMIT) 必须显式 transaction 属性**：默认 REQUIRED 在某些路径会导致事件丢失，REQUIRES_NEW 是显式"打开新事务"安全选择。
4. **乐观锁的成本**：评估端会"白跑"一次（被拒后下次重评）。本项目评估是 5 秒一次，开销可接受；高并发场景需要"事务串行 + 状态持久化"。
5. **可深入追问**：为什么用 sealed interface 而不是 enum？（enums 不能带业务方法；sealed interface 4 个 record 都能各自带字段；Java 21 sealed 与 pattern matching 完美配合 switch case。）

## 难题 3：Agent 长连接的"安全三道关" + 乐观锁离线标记

> **难度**：⭐⭐⭐（与状态机并列为安全设计典范）

### 1. 问题现象

`/ws/agent` 通道是 Java 后端的"开放门户"，面临的威胁：

1. **未授权连接溢出**：恶意客户端建立 10000 个 WS 连接占满句柄池。
2. **首帧鉴权超时**：建立连接后不发 `agent.authenticate`，白白占用连接槽位。
3. **暴力枚举 token**：发一帧 `agent.authenticate { token: "aaaa" }` 一直尝试。
4. **幽灵在线**：Agent 上报最后一次心跳后断开，DB `agent_status` 永远是 `online`；前端看到"在线"实则失联。
5. **新连接被误判离线**：断开瞬间，新连接已经上心跳，乐观锁如果写条件不对，离线状态会覆盖新心跳。

### 2. 根因分析

关键代码：

```java
// 错误实现：判活只看 WS session 状态
if (connectionRegistry.contains(serverId)) lastHeartbeat = Instant.now();
// 但 connectionRegistry 是内存对象，JVM 重启就丢；Agent 重连也会新开 session

// 错误实现 2：markOffline 不带 WHERE 条件
UPDATE servers SET agent_status='offline' WHERE id=:id
// 断开瞬间新连接上报心跳，会被这条离线 UPDATE 覆盖
```

根因：**WS session 状态 ≠ 数据库状态 ≠ 业务一致性**。

### 3. 解决思路

| 关 | 机制 |
|---|---|
| 关 1：连接级限流 | `AgentConnectionLimiter` 总 128 / 未认证 32；`AgentMessageRateLimiter` 多通道速率限制 |
| 关 2：时间级超时 | 握手后 10 秒必须发 `agent.authenticate`，否则 close |
| 关 3：内容级鉴权 | SHA-256 哈希比对（`MessageDigest.isEqual` 防时序）+ 撤销校验 |
| 离线乐观锁 | `markOfflineOnDisconnect(id, lastHeartbeatAt)` 用 WHERE 条件 `last_heartbeat_at = ?` 防误覆盖 |

```java
// websocket/AgentAuthenticationServiceImpl.java (简化)
@Transactional
public boolean authenticate(WebSocketSession session, AuthPayload p) {
    var server = serverRepo.findById(p.serverId).orElseThrow(...);
    if (server.getAgentTokenRevokedAt() != null) {
        session.close(new CloseStatus(1011, "token revoked"));  // 显式 1011 = server error
        return false;
    }
    String expectedHash = "sha256:" + sha256Hex(p.token.getBytes(UTF_8));
    boolean matches = MessageDigest.isEqual(
        expectedHash.getBytes(UTF_8),
        server.getAgentTokenHash().getBytes(UTF_8)    // 防时序攻击
    );
    if (!matches) throw new BusinessException(UNAUTHORIZED);
    // 标记为已认证 + 写入 agent_status=online + 触发首次心跳
    connectionRegistry.put(server.getId(), session);
    heartbeatService.heartbeat(server.getId(), Instant.now());
    return true;
}
```

### 6. 收获

1. **WebSocket 长连接的安全三道关**：连接级（限流）+ 时间级（超时）+ 内容级（鉴权）。
2. **乐观锁是 WS 状态同步的必备**：DB 状态变更必须带版本号或时间戳条件，不能裸 UPDATE。
3. **`MessageDigest.isEqual` 防时序**：用 `==` 比对哈希会被时间侧信道攻击，固定时间比对函数是行业惯例。
4. **status / agent_status 双字段**：是 Bug 也是设计教训。"同义字段分开维护" 一定要在第一次写之前就合并或明确文档语义。
5. **可深入追问**：为什么不用 mTLS / JWT 来鉴权 Agent？（Agent 是嵌入式终端，证书管理成本不友好；单 Token + 自研协议更易排障。）

## 难题 4：Metrics 幂等 + 乱序拒绝 + 双层防御

> **难度**：⭐⭐⭐

### 1. 问题现象

Agent 在网络抖动时会重发同一帧指标；Go Agent 端 gopsutil 有时序偏差（CPU 0.x 秒内采集两次）。

出现的问题：

1. **重复入库**：同一帧 5 秒内可能入库 2 次，MySQL 行重复，监控曲线出现"伪跳点"。
2. **乱序入库**：时钟回拨或网络重排，`collected_at=14:00:00` 的指标在 `14:00:05` 后才到；旧样本会被当成新值，触发误告警。
3. **没有 message_id**：前端（调试时）发现非法调用缺少字段，后端报 500 而不是 400。

### 2. 根因分析

```java
// 错误实现：裸插入
public void report(MetricsPayload p) {
    server = serverRepo.findById(p.serverId);
    metricsMapper.insert(p);  // 不去重，不验时间
}
// → 重复 5 次入 5 行；时钟回拨覆盖最新值
```

### 3. 解决思路

| 层 | 防御 | 实现 |
|---|---|---|
| 应用层 | `message_id` 强制 UUID | `TerminalProtocolValidator`-like 校验 |
| 存储层 | `metrics_ingestions` UNIQUE(server_id, message_id) | Flyway V11 |
| 行锁 | `SELECT ... FOR UPDATE` 锁 server 行保证顺序 | `MetricsServiceImpl.report` |
| 时间层 | `collected_at > 最后接受时间` 单调校验 | 拒绝返 40002 |

### 4. 落地实现

```java
// module/metrics/service/MetricsServiceImpl.java (完整 report)
@Transactional
public void report(WebSocketSession session, MetricsReportPayload p) {
    if (!isValidUuid(p.messageId()))                       // 1) UUID 校验
        throw badRequest("INVALID_MESSAGE_ID");
    ServerEntity srv = serverMapper.selectActiveForUpdate(p.serverId);  // 2) 行锁
    if (srv == null) throw notFound();
    try {
        ingestionsMapper.insertIgnore(p.serverId(), p.messageId(), p.collectedAt());  // 3) 幂等
    } catch (DuplicateKeyException e) {
        log.debug("duplicate metrics message {} for server {}", p.messageId(), p.serverId());
        return;   // 4) 重发静默成功
    }
    Instant lastAccepted = metricsMapper.lastCollectedAt(p.serverId);
    if (lastAccepted != null && p.collectedAt.isBefore(lastAccepted))   // 5) 单调时间
        throw badRequest("OUTDATED_METRICS");
    if (p.cpuPercent() < 0 || p.cpuPercent() > 100)        // 6) 数据合法性
        throw badRequest("INVALID_CPU_PERCENT");
    metricsMapper.insert(p);
    publisher.publishEvent(new MetricsReportedEvent(p));   // 7) AFTER_COMMIT
}
```

## 难题 5：AFTER_COMMIT 事务事件 + 实时推送 + 失败隔离

> **难度**：⭐⭐⭐（事务边界 + 副作用一致性）

### 1. 问题现象

MVP-3 核心链路：Metrics 落表 → 触发实时推送 → 触发告警评估。

问题：

1. **事务回滚却推送**：旧实现里直接 `ws.sendMessage` 在事务方法内调用，事务回滚但消息已发出。
2. **推送阻塞主流程**：一个订阅者慢，所有订阅者都受牵连。
3. **评估事务错位**：`AlertEvaluationServiceImpl` 用默认 `@Transactional`，与 AFTER_COMMIT 监听器冲突，事务没起；evals 偶发丢失。

### 2. 根因分析

```java
// 错误实现：在 @Transactional 方法内直接推送
@Transactional
public void report(...) {
    metricsMapper.insert(p);
    ws.sendMessage(new TextMessage(json(payload)));  // ← 事务回滚时已发出
    alertEval.evaluate(p);   // ← 在同一事务里，状态错乱
}
```

Spring 文档明确：`@TransactionalEventListener(AFTER_COMMIT)` 的 transactionManager 在某些路径使用上下文事务；当默认 `@Transactional` 配合时，事件触发后业务是新事务还是旧事务**不一致**。

### 3. 解决思路

1. **AFTER_COMMIT 限定触发**：只在事务真正提交后才发事件；事务回滚时所有监听器不触发。
2. **二次事件解耦链路**：Metrics 落表发 `MetricsReportedEvent` → 评估器监听到后再发 `AlertTriggeredEvent` → 推送器监听推送帧。每个事件对应独立事务。
3. **失败隔离**：发送失败不能影响其他订阅者；捕获 + 单独关闭慢会话 + log warn。

### 4. 落地实现

```java
// module/metrics/service/MetricsServiceImpl.java (发布事件)
@Transactional
public void report(...) {
    ...
    publisher.publishEvent(new MetricsReportedEvent(payload));  // AFTER_COMMIT 才真正广播
}

// websocket/MonitorMetricsPublisher.java
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
public void onMetricsReported(MetricsReportedEvent ev) {
    Set<MonitorWebSocketSession> subs = subscriptionRegistry.subscribers(ev.serverId());
    for (var session : subs) {
        try {
            session.sendMessage(new TextMessage(json("metrics.update", ev)));
        } catch (IOException | SessionWriteFail e) {
            terminationService.terminateNormally(session, "monitor_write_fail");
            log.warn("send failed for session {}: {}", session.getId(), e.getMessage());
            // 继续给其他订阅者发
        }
    }
}

// module/alert/service/AlertEvaluationServiceImpl.java
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
@Transactional(propagation = Propagation.REQUIRES_NEW)   // 关键：显式
public void onMetricsReported(MetricsReportedEvent ev) {
    // 评估可能写 alert_records / alert_states，独立事务避免和 metrics 事务绑定
    var rules = ruleMapper.selectEnabledForServer(ev.serverId());
    ...
}
```

```java
// websocket/AlertPushPublisher.java
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
public void onTriggered(AlertTriggeredEvent ev) {
    AlertPushPayload p = buildPayload(ev);
    for (var s : subscriptionRegistry.subscribers(p.serverId())) {
        try {
            s.sendMessage(new TextMessage(json("alert.push", p)));
        } catch (Exception e) { terminationService.terminateNormally(s, "alert_write_fail"); }

```

### 5. 真实验证

- `docs-SuMon/Develop-log/20260721-WebSocket监控通道缺陷修复.md`：原来 `BusinessException` 静默吞错被改回显式 log；
- `20260725-V11真实验证与P2-1限流实现.md`：Spring 6.2 拒绝 `@TransactionalEventListener + 默认 @Transactional` 组合 → 显式 `REQUIRES_NEW`；
- H2 集成测试：事务提交后 AFTER_COMMIT 广播 1 次，回滚后广播 0 次（`20260722-AFTER_COMMIT事务集成测试.md`）；
- Apifox 实时链路验证。

### 6. 收获

1. **副作用必须在事务边界外**：最干净的做法是 AFTER_COMMIT 事件，绝不直接在 @Transactional 方法内 sendMessage。
2. **链路解耦用"事件链"**：每个事件对应独立事务 + 独立监听器，失败局部化。
3. **Spring 6.2 的限制**：AFTER_COMMIT + 默认事务属性行为不一致，必须显式声明。
4. **失败隔离用 try/catch**：所有 sendMessage 必须包 try/catch，单点失败不能炸链路。
5. **可深入追问**：为什么不用 Spring TransactionSynchronization 直接注册回调？（底层机制相同；事件机制对单元测试更友好，可以 mock publisher。）

```java
// ssh/SshConnectionTester.java (简化)
private SshTestResult doConnect(ServerEntity s) {
    if (!outboundPolicy.isAllowed(s.sshHost(), s.sshPort()))
        throw new SshConnectionException(TARGET_FORBIDDEN, "port not allowed", null);
    if (!rateLimiter.tryAcquire()) throw new SshConnectionException(CONNECTION_LIMIT_REACHED, "...", null);
    try (var client = new SshClient()) {
        client.loadKnownHosts(new ByteArrayResource(s.getSshHostKeyFingerprint()));
        client.connect(s.sshUser, s.sshHost, s.sshPort)
              .verify(new FingerprintVerifier(s.getSshHostKeyFingerprint()));  // 强制验证
        client.authPassword(s.sshUser, CredentialCipher.decrypt(s.getSshPasswordEncrypted(), AAD(s.id())));
        return SshTestResult.ok(client.getTransport().getRemoteHostKey(), Instant.now());
    } catch (UserAuthException e) {
        throw new SshConnectionException(AUTHENTICATION_FAILED, e.getMessage(), e);  // → 50003
    } catch (ConnectionException e) {
        throw new SshConnectionException(CONNECTION_FAILED, e.getMessage(), e);     // → 50002
    } catch (TransportException e) {
        if (!serverHasHostKey(s.id())) throw new SshConnectionException(HOST_KEY_NOT_CONFIRMED, ...);  // → 40901
        throw new SshConnectionException(HOST_KEY_MISMATCH, "fingerprint changed", e);  // → 40902
    }
}
```

- 点击"登录"按钮无反应；
- DevTools Network 显示 0 个请求；
- `console` 报 `TypeError: Cannot read properties of undefined (reading 'randomUUID')`；
- 同样的接口在 HTTPS 下完美工作。

### 2. 根因分析

```ts
// web-vue-SuMon/src/api/client.ts (改造前)
const correlationId = crypto.randomUUID();        // ← 在非安全上下文下 undefined
req.headers['X-Correlation-ID'] = correlationId;
```

W3C 规范：`crypto.randomUUID` 只在 **secure context**（HTTPS / localhost / 127.0.0.1）可用。明文 HTTP 下 `window.crypto` 是 `undefined`，导致请求拦截器同步抛 TypeError，axios 链断裂。

更糟糕的是 `services/terminal-ws.ts` `terminal.open` 帧的 `message_id` 也用了 `crypto.randomUUID` —— 同样的问题。

```ts
// web-vue-SuMon/src/services/terminal-ws.ts (改造前)
const messageId = crypto.randomUUID();  // HTTP 下崩
this.socket.send(JSON.stringify({ type: 'terminal.open', message_id: messageId, ... }));
```

后果：
1. **登录失败**：axios 拦截器抛错，请求根本没发出，按钮"卡死"；
2. **终端黑框**：后端 `TerminalProtocolValidator` 看到 `message_id` 非 UUID 返 40003；
3. **xterm cols=2**：另一个独立坑——`t.open()` 后立即 `fit()` 时容器宽度为 0，导致发给后端的 cols=2，终端几乎无法使用。

### 3. 解决思路

1. **`crypto.randomUUID` 降级**：检测 `crypto` 和 `crypto.randomUUID` 是否可用，失败时用 `Date.now() + Math.random()`；
2. **统一工具函数** `newCorrelationId()`：所有需要 UUID 的地方复用；
3. **xterm `onSocketReady` 重 fit**：等容器布局完成后调 fit 而非 `t.open` 立即 fit。

### 4. 落地实现

```ts
// web-vue-SuMon/src/utils/secure-random.ts
export function newCorrelationId(): string {
  if (typeof crypto !== 'undefined' && typeof crypto.randomUUID === 'function') {
    return crypto.randomUUID();
  }
  // 降级：RFC 4122 v4 用 getRandomValues 拼
  if (typeof crypto !== 'undefined' && typeof crypto.getRandomValues === 'function') {
    const buf = new Uint8Array(16);
    crypto.getRandomValues(buf);
    // 强制 v4 (set high nibble to 0x4) 和 variant (set high 2 bits to 10)
    buf[6] = (buf[6] & 0x0f) | 0x40;
    buf[8] = (buf[8] & 0x3f) | 0x80;
    const hex = Array.from(buf, b => b.toString(16).padStart(2, '0')).join('');
    return `${hex.slice(0,8)}-${hex.slice(8,12)}-${hex.slice(12,16)}-${hex.slice(16,20)}-${hex.slice(20)}`;
  }
  return `ts-${Date.now().toString(16)}-${Math.floor(Math.random() * 1e9).toString(16)}`;
}
```

- `docs-SuMon/Difficulty-log/20260730-前端登录点击无反应-crypto-randomUUID非安全上下文.md`：登录 Bug 全过程；

- 修复后浏览器真实联调 IAB 验证（`20260729-前端B-038真实浏览器联调收口.md`）。

### 6. 收获

1. **安全上下文是 Web 平台基石**：`crypto.randomUUID` / `getRandomValues` / Service Worker 等只在 HTTPS 或 localhost 可用。
2. **降级而不是抛错**：feature detection + polyfill，对用户透明。
3. **统一工具函数**：所有 UUID 需求走同一个 `newCorrelationId`，避免到处复制降级代码。
4. **async UI 生命周期**：xterm fit 不能立即触发，要等 `await nextTick()` 或 `requestAnimationFrame`。
5. **全栈视野**：前端一个 `crypto.randomUUID` 失败能牵连登录 + 终端两个业务域；跨端排错必须前后端都看。
