## 三、关键设计权衡（8 条 "Why We Chose X"）

### 1. 单体模块化 vs 微服务

**选择**：单体 + 模块化（`module/{auth,admin,server,metrics,alert,terminal,system}`）。

**理由**：
- MVP-1 单 JVM 已能撑 128 Agent（连接限流配置项）；
- 模块边界清晰 = 服务内部 `package-by-feature`，未来拆微服务时改 deployment unit 即可；
- 不需要 Service Mesh、不需要分布式事务，开发效率高 10x。

**演进路径**：当单实例 JVM 撑不住时才考虑拆"评估服务""WebSocket 网关服务"独立部署。

### 2. WebSocket 双通道（Agent 首帧 vs Monitor Ticket）

**选择**：两个 `/ws/agent` 和 `/ws/monitor` 端点，**不复用**。

**理由**：
- Agent 是 Go 原生客户端，无法注入 Authorization header → 用首帧；
- 浏览器是 Web，WebSocket API 强制 URL Query → 用 ticket；
- 职责单一（Agent 上行 vs Browser 下行）便于分别限流 / 鉴权。

**对比**：方案 B 是"统一一个端点 + Path 参数区分"，被 reject 因为 session pool 混合、限流策略难分。

### 3. AFTER_COMMIT 事件 vs 消息队列

**选择**：`@TransactionalEventListener(AFTER_COMMIT)`。

**理由**：
- MVP 体量够用，零额外组件；
- 事件在 JVM 内传递，延迟 < 1ms；
- 直接发 Spring Bean 调用，AOP 可观测。

**演进路径**：当出现"事件消费慢拖累主流程"或"多 JVM 跨实例广播"需求时，引入 RabbitMQ 替换；MVP-10 已规划。

### 4. AES-GCM 凭证 vs Vault / KMS

**选择**：本地 `CredentialCipher` + 环境变量密钥。

**理由**：
- MVP 体量无需外部依赖；
- 学习成本 vs 价值比合理；
- 信封格式 `v1:` 留升级空间。

**演进路径**：当出"多租户 / 多服务实例共享密钥轮换"需求时，集成 Vault 或 KMS。

### 5. 告警状态机 + 乐观锁 + 唯一索引 vs if-else 简单实现

**选择**：sealed interface 三件套。

**理由**：
- 业务一致性要求（持续越界不能写 N 条 record）；
- 5 元组重复规则必须 DB 层兜底（前端校验不可信）；
- 状态机让"评估逻辑"和"持久化逻辑"解耦。

**对比**：方案 B 是"Triggered 字段 + 简单 cron"，被 reject 因为乱序事件和并发评估容易丢触发。

### 6. 终端元数据入表 vs 全量 PTY 数据入库

**选择**：`session_id`、`shell`、`open_message_id`、`user_id`、`status` 入表；**PTY 输入输出不入库**。

**理由**：
- 输入可能含密码（`sudo passwd`），存盘违反审计最小原则；
- 存储爆炸（连续操作每秒 1KB×N 小时）；
- 元数据足以排障（谁、何时、开多久、为何关）。

**演进路径**：若要"命令审计 + 录像回放"，单独开 `terminal_session_bytes` 分片存储 + 加密 + 留存策略。

### 7. 软删除 + `delete_token` vs 硬删除

**选择**：软删除（`deleted=1` + `deleted_at` + `delete_token`）。

**理由**：
- 审计可追溯（"那台服务器曾经是谁管的、什么时候删的"）；
- `delete_token=UUID` 让 host 唯一约束允许"删除后重建同名 server"；
- `AlertEvaluationServiceImpl` 等查询统一 `WHERE deleted=0`。

**对比**：方案 B 是"硬删除 + 单独 audit 表"，运维成本高，违规风险高。

### 8. 行锁 vs 乐观锁 vs 无锁

**选择**：根据场景选：
| 场景 | 选择 | 理由 |
|---|---|---|
| Agent 指标入库 | 行锁 `SELECT ... FOR UPDATE`（按 server_id） | 高频 5s/次，必须保证顺序 |
| 告警评估更新 last_triggered | 乐观锁 `version` | 低频，避免无效竞争 |
| 首管理员注册 | 行锁 `auth_bootstrap_state WHERE id=1` | 单行锁，竞争可控 |
| SSH 凭据更新 | 无特殊锁（update 一次性） | 低频写 |

### 9. H2 + MySQL 双轨测试 vs Testcontainers

**选择**：H2（Mapper 集成）+ 真实 MySQL（`*IT.java` 仅在 `mysql-validation` profile）+ URL 沙箱。

**理由**：
- H2 启动快（< 1s），CI feedback 快；
- MySQL 子集兼容 ≠ 完全兼容，必须真实环境走一遍 SQL；
- Testcontainers 需要 Docker，开发环境可移植性差。

**演进路径**：上 Docker CI 后切换 Testcontainers，省"URL 沙箱"重复校验。

## 四、安全设计纵览

| 层 | 防御机制 |
|---|---|
| 传输 | 本机依赖 Nginx / 计划上 HTTPS / WSS |
| 鉴权 | JWT（72h）+ Agent Token（SHA-256）+ Monitor Ticket（一次性 30s） |
| 授权 | RBAC 矩阵（admin / user），Controller 层 `@PreAuthorize` 显式声明 |
| 输入校验 | Bean Validation + 字段白名单（排序字段、Metric 枚举、Operator 枚举） |
| 防重放 | Agent Token + AAD（AES-GCM）+ Ticket 一次性 + UUID 幂等 |
| 速率限制 | 多通道令牌桶（agent 总连接 / 心跳 / 指标 / 终端控制帧 / 终端输出字节） |
| 请求跟踪 | `X-Request-ID` 服务端生成 + MDC + Logback |
| 异常处理 | `GlobalExceptionHandler` + 25 个 ErrorCode；只记字段名不记值 |
| 凭据保护 | AES-256-GCM 信封；环境变量注入；JavaScript 端从不上传明文密码（仅注册时） |
| 敏感数据 | 日志脱敏（不打印 JWT / Token / 密码 / SSH 凭据） |

## 五、可观测性现状

| 项 | 现状 | 缺口 |
|---|---|---|
| **日志** | Logback + MDC + 结构化字段 | ELK / Loki 收集未接入 |
| **指标** | `/api/health`、`/api/ready` | 应用层 Micrometer / Prometheus 未接入 |
| **链路追踪** | `X-Request-ID` 端到端 | 分布式追踪（OpenTelemetry / Zipkin）未接入 |
| **告警** | 业务告警（用户自配） | 平台告警（磁盘满 / OOM）未接入 |
| **APM** | — | Spring Boot Actuator 未引入 |

**演进路径**：Actuator + Prometheus + Grafana → OpenTelemetry → 接入公司监控体系。
