# SuSuMonitor 下一步后端实现与 Apifox/OpenAPI 计划

## 目标

下一步先把 Java 后端从“可编译的工程骨架”推进到“可通过 Apifox 调用的最小后端基础接口”。优先实现横切基础能力和 `GET /api/health`、`GET /api/ready`，同时补齐 OpenAPI 3.0 JSON 文档，让 Apifox 能导入并测试接口。

## 当前已完成的后端部分

- Maven + Spring Boot 3.4.7 + Java 21 工程已建立：`server-java-SuMon/pom.xml`。
- 后端启动类已建立：`server-java-SuMon/src/main/java/com/susumonitor/server/SuSuMonitorServerApplication.java`。
- 已启用 `@ConfigurationPropertiesScan` 和 `@EnableScheduling`。
- 已有类型化配置类：`server-java-SuMon/src/main/java/com/susumonitor/server/config/AppProperties.java`。
- 已有临时安全配置：`server-java-SuMon/src/main/java/com/susumonitor/server/security/SecurityConfig.java`，当前所有请求放行，仅适合骨架阶段。
- 已有配置文件：`application.yml`、`application-local.yml`、`logback-spring.xml`、`.env.example`。
- `logback-spring.xml` 已预留 `request_id` MDC 字段，但还没有过滤器写入。
- 已有基础 context 测试：`server-java-SuMon/src/test/java/com/susumonitor/server/SuSuMonitorServerApplicationTests.java`。
- `api-test/susumonitor.http` 已有接口调试模板，但后端 Controller 尚未实现。
- `docs-SuMon/OpenApi-SuMon/` 当前无正式 OpenAPI JSON 文件。

## 当前后端怎么测试

当前没有可通过 Apifox 成功调用的业务 REST 接口。现在能测试的是“工程骨架能否通过 Spring 上下文测试”。

推荐当前验证方式：

1. 在 `server-java-SuMon/` 目录执行 `mvn test`。
2. 预期只运行 `SuSuMonitorServerApplicationTests.contextLoads()`。
3. 该测试排除了 DataSource 和 Flyway 自动配置，所以不依赖本机 MySQL。
4. 如果本机 Maven 默认不是 Java 21，需要先确保 `JAVA_HOME` 指向 Java 21。

当前不推荐用 Apifox 测试业务路径，因为 `/api/health`、`/api/ready`、认证、管理员、服务器等接口源码尚未实现。即使启动后端，这些路径也没有对应 Controller。

## 下一步推荐实现范围

第一阶段只实现 MVP-1 横切基础能力，不做认证和服务器 CRUD，目标是尽快形成 Apifox 可测闭环。

本阶段实现：

1. 统一响应结构。
2. 统一错误码。
3. 全局异常处理。
4. `request_id` 过滤器：请求进入时生成或透传 `X-Request-ID`，写入响应头和日志 MDC。
5. `GET /api/health`：应用存活检查，不依赖数据库。
6. `GET /api/ready`：数据库连通性检查。
7. OpenAPI 3.0 JSON 文档：覆盖 health、ready、统一响应、错误响应、`X-Request-ID` header。
8. 更新 `api-test/susumonitor.http`，保证和已实现接口一致。
9. 更新后端 README 和开发日志。

暂不在本阶段实现：

- 用户注册、登录、JWT、管理员审核。
- Flyway 业务表结构。
- 服务器 CRUD。
- SSH 凭据加密和 SSH 测试。
- WebSocket、Agent、指标、告警。

原因：这些都依赖稳定的响应、错误、异常和 request_id 基础能力。先把基础接口跑通，Apifox/OpenAPI 契约稳定后再扩展。

## 统一响应设计

成功响应：

```json
{
  "code": 0,
  "message": "success",
  "data": {}
}
```

错误响应：

```json
{
  "code": 40000,
  "message": "bad request"
}
```

第一阶段错误码：

- `0`: success
- `40000`: bad request
- `40002`: invalid request parameter
- `50000`: internal server error
- `50001`: database error

后续认证阶段再扩展并实际使用：

- `40001`: invalid username or password
- `40100`: unauthorized
- `40300`: forbidden
- `40400`: resource not found
- `40900`: resource conflict
- `50002`: ssh connection failed
- `50003`: agent offline

## request_id 设计

实现规则：

1. 如果请求 header 带 `X-Request-ID` 且非空，后端沿用该值。
2. 如果请求没有 `X-Request-ID`，后端生成 UUID。
3. 响应 header 固定返回 `X-Request-ID`。
4. 请求处理期间写入 MDC key：`request_id`。
5. 请求结束后清理 MDC，避免线程复用污染。

## health/ready 实现细节

`GET /api/health`：

- 不访问数据库。
- 返回服务存活状态。
- 建议响应 data：`status`、`application`、`timestamp`。

示例：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "status": "UP",
    "application": "susumonitor",
    "timestamp": "2026-07-13T10:00:00+08:00"
  }
}
```

`GET /api/ready`：

- 使用 `DataSource` 获取连接，执行轻量检查。
- 成功返回 `database: ok`。
- 数据库异常时返回 HTTP 500 和错误码 `50001`。
- 不输出数据库密码或连接串中的敏感信息。

示例成功响应：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "status": "UP",
    "database": "ok",
    "timestamp": "2026-07-13T10:00:00+08:00"
  }
}
```

## Apifox 测试计划

当前阶段测试：

- 当前后端无已实现 REST 接口，Apifox 暂时没有可验证的业务接口。
- 当前只能以 `mvn test` 验证工程骨架。

完成第一阶段后，Apifox 测试步骤：

1. 在 Apifox 中导入 `docs-SuMon/OpenApi-SuMon/openapi-system.json`。
2. 设置环境变量 `baseUrl = http://localhost:18080`。
3. 启动后端：在 `server-java-SuMon/` 执行 `mvn spring-boot:run`。
4. 调用 `GET /api/health`。
5. 检查 HTTP 状态码为 200。
6. 检查响应 JSON：`code = 0`、`message = success`、`data.status = UP`。
7. 检查响应 header 包含 `X-Request-ID`。
8. 调用 `GET /api/ready`。
9. 若本机 MySQL 已初始化并可连接，预期 HTTP 200，`data.database = ok`。
10. 若 MySQL 不可连接，预期 HTTP 500，`code = 50001`，用于验证错误响应结构。

Apifox 环境建议：

- 环境名：`local`
- `baseUrl`: `http://localhost:18080`
- 暂时不配置 Token，认证接口后续实现后再增加 Bearer Token 环境变量。

## OpenAPI 文档计划

第一阶段只写一个系统接口文档：

- 文件：`docs-SuMon/OpenApi-SuMon/openapi-system.json`
- 格式：OpenAPI `3.0.3`
- server：`http://localhost:18080`
- tags：`system`
- paths：`/api/health`、`/api/ready`
- components.schemas：`ApiResponseHealthStatus`、`ApiResponseReadyStatus`、`ErrorResponse`、`HealthStatus`、`ReadyStatus`
- components.headers：`XRequestId`

接口定义要求：

- 每个接口都声明 `X-Request-ID` 响应头。
- `GET /api/health` 响应 200。
- `GET /api/ready` 响应 200 和 500。
- 所有响应示例使用统一响应结构。
- 不在第一阶段 OpenAPI 中声明 JWT bearerAuth，避免 Apifox 误以为 system 接口需要认证。

后续第二阶段再补：

- `openapi-auth.json`：注册、登录、退出、当前用户、管理员审核。
- `openapi-server.json`：服务器 CRUD、状态、SSH 测试。
- 或最终合并为 `openapi.json` 作为总文档。
